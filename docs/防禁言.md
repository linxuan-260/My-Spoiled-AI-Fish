# 群聊防禁言指南

被踢/被禁言通常来自两个方向：**QQ 平台风控**（发得太勤、内容雷同、短时间内大量主动消息）和**群管理**（刷屏、跑了不该跑的自动行为）。这份清单就是按这两条排的。

## 一、别让她"主动说话"太勤

真正的风险不是回复，而是**没人叫她、她自己冒出来**。这个项目里所有主动行为都在下面几个参数上：

| 参数 | 位置 | 默认 | 建议 |
|---|---|---|---|
| `trigger.read_prob` | qzone | `0.001` | **保持 0.001 或更小**。这是「每来一条消息就随机去读对方说说」的概率，调大等于让机器人到处翻别人空间 |
| `publish_cron` | qzone | `30 23 * * *` | 一天一次足够；改成每几小时一次很容易被判刷屏 |
| `publish_offset` | qzone | `600` | **别设 0**。固定整点发是最容易被识别的特征 |
| `comment_cron` | qzone | `0 8 * * *` | 一天一次 |
| `comment_offset` | qzone | `600` | 同上，保留抖动 |
| `L3_life.tick_seconds` | fish_memory | `1200` | 20 分钟一拍是内部计算节奏，不直接发消息，按需调 |
| `L3_life.browse_interval_seconds` | fish_memory | `7200` | 自主探索，2 小时一次；低于 1 小时意义不大还费钱 |

### 为什么抖动这么重要

`publish_cron = "30 23 * * *"` 配 `publish_offset = 600`，实际执行时间会散在 23:20–23:40 之间。如果 `offset = 0`，每天 23:30:00 整点发一条，这个规律比内容本身更显眼。

历史 bug 佐证：早期调度器用 `now` 当参考点算下一次执行，在 ±600s 窗口里反复命中「今天 22:30」，结果一晚连发 3 条。现在参考点改成了 `self._last_base_time or now`。**改调度代码时这个不能动。**

## 二、说要有硬闸，不能只靠提示词

`service.publish_post` 里有一层代码级节流（不在配置里）：

- 两条说说间隔 **≥ 3 小时**
- 每天 **≤ 6 条**

超了直接抛错，LLM 想刷也刷不动。状态存在 `plugin_data/astrbot_plugin_qzone/publish_guard.json`：

```json
{"date": "2026-11-01", "count": 2, "last_ts": 1793497026}
```

如果发现她还能连发，先看这个文件是不是没生成（说明有代码路径绕过了 `publish_post`）。

## 三、不要在群里外发别人的内容

`trigger.send_read_card` **默认 `false`**，别去开。

它的作用是把读到的好友说说渲染成卡片（含图片）发到管理群。如果对方设了「好友可见」，内容就这么漏出去了 —— 这既是隐私事故，也是被投诉/拉黑的常见原因。

同理，`trigger.send_admin = true` 时卡片只私发给管理员，比起发到群里更保守。

## 四、忽略名单

别再让她对某些人自动读说说/评论：

```json
// qzone config
"source": { "ignore_users": ["<QQ号>", "<另一个QQ号>"] }
```

`is_ignore_user()` 会同时过滤「概率触发」这条路径。名单里应该放：陌生人、容易被冒犯的人、以及**你自己的测试号**。

## 五、权限边界

管理类命令（发说说、删稿、查看访客等）只给管理员：

```python
@filter.permission_type(filter.PermissionType.ADMIN)
```

自定义插件里的危险动作同理。群里任何人都能触发的写操作（发说说、@全体、改配置）都算高危。

## 六、回复频率（AstrBot 侧）

本仓库不控制"要不要回复" —— 那是 AstrBot 自己的唤醒策略。原则：

- **优先「被 @ 才回」**，其次才是概率唤醒
- 群聊里连续回复要有冷却，别让两条消息触发两次模型调用
- 戳一戳、表情回应这类高频事件不要直接进 LLM

## 七、已经被禁言了怎么办

1. 先看频率：`journalctl -u astrbot --since '1 hour ago' | grep -c "Prepare to send"`，算一下每小时的发送条数
2. 查被动触发：是不是 `read_prob` 被改大了，或者有定时任务在整点扎堆
3. 关掉主动类任务（`browse_enabled=false`、`publish_cron=""`、`comment_cron=""`）观察一天
4. 恢复后**一个一个开回来**，每次观察 24 小时

## 推荐基线配置

```json
{
  "trigger": {
    "read_prob": 0.001,
    "publish_cron": "30 23 * * *",
    "publish_offset": 600,
    "comment_cron": "0 8 * * *",
    "comment_offset": 600,
    "send_read_card": false,
    "send_admin": true,
    "like_when_comment": true
  }
}
```

```json
{
  "L3_life": {
    "tick_seconds": 1200,
    "browse_enabled": true,
    "browse_interval_seconds": 7200,
    "llm_activity_prob": 0.35
  }
}
```
